# cofa-starter

Codex CLI로 업무형 과제를 풀 때 쓰는 개인 시작 세팅과 행동 방침입니다.
작업 규칙(AGENTS.md), 프로젝트 스킬 4개, 기록 템플릿 4개, 웹 과제용 참고 문서 2개(DESIGN.md, ARCHITECTURE.md)로 구성됩니다. 과제 답안이나 코드는 포함하지 않습니다.

> 막히면 이 문서로 돌아온다.
> **"무엇을, 어떤 제약으로, 어디까지, 어떻게 확인할지"는 매번 내가 정한다.**
> **AI의 "완료"는 내가 직접 확인하기 전까지 완료가 아니다.**

## 0. 시작 (2분)

```bash
git clone https://github.com/<계정>/cofa-starter /tmp/starter
export NEXT_TELEMETRY_DISABLED=1                          # 통계 전송 끄기 (새 터미널마다)
WITH_CONTEXT7=1 WITH_NEXT_MCP=1 bash /tmp/starter/bootstrap.sh   # MCP 없이: bash /tmp/starter/bootstrap.sh
codex                                                     # → /status 모델·권한, /mcp 서버 확인
```

MCP·스킬 세부는 10장 "도구 세팅".

다른 터미널 탭에서 `less /tmp/starter/README.md` 로 이 문서를 열어 둔다.
단계별 풀이 예시는 `less /tmp/starter/WORKFLOW.md`.

| 파일 | 언제 | 어떻게 |
|---|---|---|
| `AGENTS.md` | 항상 (자동) | Codex가 자동으로 읽음. 과제에 맞는 규칙은 "AGENTS.md에 ○○ 추가해" |
| `DECISIONS.md` | 합의 후, 구현 중, 마무리 | 문제 정의 → 구조 → 검증 → 운영 리스크 → 한계 |
| `VERIFY.md` | 단계마다 | 내가 직접 돌린 검증 기록 |
| `$handoff` | 단계 끝날 때 | HANDOFF.md 갱신 + 커밋 → 필요하면 `/new` |
| `$verify-manual` | 단계 끝날 때 | 내가 돌릴 검증 절차 생성 → 내가 실행 → `$verify-manual 결과 …`로 기록 |
| `$ai-decision-log` | AI 제안을 바꾸거나 거절할 때 | `$ai-decision-log 캐시 제안 거절. 하루 1회 갱신이라 불필요` |
| `$verify-before-submit` | 제출 15~20분 전 | 실행·요구 사항·보안·검증 기록·운영 리스크·구조·화면 상태 점검 |
| `docs/DESIGN.md` | 웹 화면 만들 때 | "DESIGN.md의 ○○ 패턴을 따라" |
| `docs/ARCHITECTURE.md` | 웹 앱 구조 잡을 때 | "ARCHITECTURE.md 3장에서 필수(●)만 만들어" |

스킬이 안 먹히면 같은 내용을 말로 시키면 된다.
Codex는 매 답변 끝에 `문서 갱신: …` 한 줄을 보고한다 (AGENTS.md 규칙). **이 줄을 보고 빠진 기록을 잡는다.**
웹 과제가 아니면 `docs/` 폴더는 지워도 된다.

## 1. 전체 흐름 (180분)

| 시간 | 단계 | 끝났다는 증거 |
|---|---|---|
| 0~10 | 세팅 | 첫 커밋 |
| 10~40 | **조사 + 담당자 대화 + 서면 합의** | DECISIONS.md 1~4, `$handoff`, `/new` |
| 40~50 | (웹) 구조 세팅 + 서체 | ARCHITECTURE.md 필수 폴더, DECISIONS.md 5번, 빈 화면이 0.0.0.0:3000에서 뜸 |
| 40~130 | **단계별 구현 → 내가 직접 검증 → 커밋** 반복 | 단계마다 VERIFY.md에 "실행자: 나" 기록 |
| 핵심 완성 시 | 인계 + 검토 세션 | `$handoff`, `/new`, 검토 보고 |
| 130~150 | 운영 리스크 대비 (작게) | 리스크 표 채움, 작은 대비 구현 |
| 150~165 | 최종 점검 + 문서 | `$verify-before-submit`, DECISIONS.md 5~11 |
| 165~180 | 제출 | 종료 10분 전 제출 시작, 코드·DECISIONS.md·VERIFY.md 다시 읽기 |

**Codex가 일하는 동안 기다리지 않는다.** 그 시간에 담당자 대화, 문서, 내 검증 실행.
**승인 대기로 멈춰 있지 않은지** 수시로 확인한다.

## 2. 담당자 대화 (소통)

**처음 3분은 해결책 단어("자동화", "AI") 없이**
1. 에피소드: "최근에 이 일 때문에 곤란했던 일 하나만 얘기해 주실 수 있어요?"
2. 임시방편: "지금은 어떻게 하고 계세요?"
3. 정량화: "일주일에 몇 번, 몇 분씩 걸려요?"
4. 당사자: "결과물은 누가, 언제, 어디서 쓰나요?"
5. 경계: "이번에 꼭 할 것과 안 해도 되는 건요?"

**데이터 의문은 근거를 들고**
- ○ "수량이 빈칸이거나 -2인 행이 있던데, 어떻게 보여 드릴까요?"
- × "데이터에 특이한 점 있나요?"

**운영 상황도 물어본다** (나중에 리스크 질문의 근거가 된다)
- "이 화면을 관리하는 분은 몇 명이에요? 동시에 고치는 경우도 있나요?"
- "이게 안 열리면 사용하시는 분들은 어떻게 되나요?"
- "데이터는 얼마나 자주, 누가 바꾸나요?"
- "다른 사람 정보가 보이면 안 되는 게 있나요?"

**합의는 글로 정리해 확인받기**
```
정리하면 - 문제: / 만들 것: / 안 만들 것: / 성공 기준: / 제약:
이렇게 진행해도 될까요?
```

담당자 말은 **요약해서** Codex에 넘긴다. 대화 통째 붙여넣기 금지.

## 3. Codex 지시 방식 (의도: 변별력 최대)

### 모든 위임에 4요소

```
[목표]     무엇을 만든다
[제약]     하지 말 것, 지켜야 할 규칙, 건드리지 말 범위
[완료 기준] 어떤 결과가 나오면 끝인가 (숫자·케이스로)
[검증]     무엇을 실행해서 보여 줄 것인가 + 내가 직접 돌릴 확인 명령 → 커밋 → 멈춰
```

예:
```
[목표] 재고 합산과 상태 판정 함수를 만들어.
[제약] 빈칸·음수는 0으로 처리하지 말고 "확인 필요". 단가 컬럼은 다루지 마. 새 라이브러리 금지.
[완료 기준] 빈칸, 음수, 안전재고와 같은 값, ALL 유형 테스트 통과.
[검증] 테스트 결과와 대표 2건의 판정 결과를 보여 줘. 그리고 내가 직접 돌릴 확인 명령 2~3개를
      입력 데이터에서 계산한 기대값과 함께 따로 적어 줘. 커밋하고 멈춰.
```

### 단계별 지시 템플릿

**① 조사 (아무것도 만들지 않기)**
```
README와 제공 파일을 모두 읽고 조사해. 아직 어떤 파일도 만들거나 고치지 마.
- 파일별 형식, 컬럼 의미, 행 수, 인코딩
- 빈칸, 음수, 중복, 표기 불일치 같은 이상 데이터
- 민감해 보이는 정보 (개인정보, 단가, 사외비)
- README에 언급되지 않은 파일이나 폴더
```

**② 계획 (코드 금지)**
```
합의 내용: (요약)
DECISIONS.md 1~4번을 채우고 커밋해. 그다음 구현 계획을 단계별로 보여 줘.
각 단계마다 완료 기준과 검증 방법을 붙이고, 입력 반영·계산·게시·조회를 어떤 모듈로 나눌지도 보여 줘.
아직 코드는 쓰지 마.
```

**③ 계획 쳐 내기**
```
○번, ○번은 빼. (이유: 담당자가 불필요하다고 함)
1단계만 하고 멈춰. 결과 보여 주고 커밋.
```

**④ 결과 확인 (완료 선언을 믿지 않기)**
```
"완료"라고 하지 말고 실행 결과를 보여 줘.
테스트에 ○○ 케이스가 없어. 추가해서 다시 돌려.
```

**⑤ 판단과 계산 분리**
```
판정·계산은 고정 코드와 테스트로 해. AI가 판단하게 하지 마.
○○은 초안만 뽑아 줘. 내가 검토해서 확정할게.
```

**⑥ 맥락 갱신**
```
담당자 확인 결과 ○○가 바뀌었어. DECISIONS.md에 반영하고 남은 계획을 갱신해.
```

**⑦ 세션 전환**
```
$handoff
/new
AGENTS.md와 HANDOFF.md 읽고 '다음 세션의 첫 행동'부터 이어가.
```

**⑧ 검토 세션 (핵심 기능 완성 후 1회)**
```
$handoff
/new
너는 이번 세션에서 검토자 역할이야. 코드를 고치지 마.
AGENTS.md, HANDOFF.md, DECISIONS.md, VERIFY.md를 읽고, 합의된 요구 사항 대비
빠진 것, 틀린 것, 보안 위험, 운영 리스크를 근거(파일·함수)와 함께 표로 보고해.
```
→ 보고를 보고 **내가** 고칠 것을 고른 뒤 다시 구현 지시.

### 점수 차를 만드는 장면 (기록에 꼭 남기기)

1. **AI 제안을 이유와 함께 거절** → `$ai-decision-log`
2. **AI 오류를 내 검증으로 잡아냄** ("불변 조건을 돌려 보니 ○○가 2건 나와. 원인 찾아")
3. **판단과 계산의 경계를 내가 정함** (판정은 코드, AI는 초안)
4. **AI 테스트를 의심함** ("이 검사를 지웠는데 테스트가 통과해. 테스트를 고쳐")

### 세부 항목 체크

- [ ] 문제·제약 정의: 구현 전 조사, 제약 명시
- [ ] Output 목표 구체화: 완료 기준을 숫자·케이스로
- [ ] 작업 분해·위임: 계획을 받고 내가 잘라내고 순서 결정
- [ ] 검증 루프: 단계마다 내가 직접 실행, 틀린 것 지적
- [ ] 의도 갱신·맥락 유지: 담당자 변경 사항 즉시 반영, handoff
- [ ] 재사용 체계: AGENTS.md, 스킬, 템플릿

## 4. 내가 직접 검증하기

AI가 만든 함수를 AI가 만든 테스트로만 확인하면 같은 착각을 두 번 할 수 있다.
**AI와 다른 경로로 정답을 확인**하고, **내 터미널에서 실행한 흔적**을 남긴다.

| 방법 | 내용 | 예시 |
|---|---|---|
| 작은 케이스 | 손으로 답을 아는 최소 데이터 | 3건 입력 → 결과 2개가 나와야 함 (손 계산) |
| 불변 조건 | 어떤 결과든 지켜야 할 규칙을 별도 쿼리로 센다 | 모든 대상이 정확히 한 번 배정 / 용량 초과 0건 / 시간 제약 위반 0건 |
| 다른 경로 재계산 | 화면·API 숫자를 DB 쿼리·원본 파일로 따로 계산 | 화면 합계 = `SELECT COUNT(*)` |
| 일부러 깨뜨리기 | 잘못된 입력, 동시 요청, 서버 중단 | 컬럼 빠진 파일 업로드 / curl 2개 동시 저장 / 서버 끄고 조회 |
| 테스트를 테스트 | 핵심 검사를 임시로 지우면 테스트가 실패해야 함 | 용량 검사 삭제 → 테스트 실패 확인 → 되돌리기 |
| 화면 직접 조작 | 사용자처럼 눌러 본다 | 입력 → 결과 → 설정 변경 → 반영 확인 |

**단계마다 루프**
1. `$verify-manual` → Codex가 절차와 기대값(근거 포함)을 VERIFY.md에 추가
2. **내 터미널 탭에서 직접 실행**
3. `$verify-manual 결과 1번 통과, 2번 용량 초과 2건` → 기록
4. 다르면 근거를 들고 수정 지시 → 재검증 → 실패와 수정 기록은 지우지 않는다

"작은 케이스"와 "테스트를 테스트"는 단계마다 하나씩은 넣는다. AI를 의심했다는 가장 강한 증거다.

## 5. 구조와 운영 리스크

### 책임 분리 (계획 단계에서 정한다)

| 계층 | 책임 | 원칙 |
|---|---|---|
| 입력 반영 | 업로드·검증·저장, 실패 행 보고 | 잘못된 입력이 들어와도 기존 확정본은 안전 |
| 계산 | 도메인 로직 | DB·HTTP를 모르는 순수 함수, 단독 테스트 |
| 게시 | 결과 확정, 버전, 변경 이력 | 초안 → 확인 → 게시, 이전 버전으로 되돌리기 가능 |
| 조회 | 확정 결과 읽기 전용 | 계산을 직접 돌리지 않음, 본인 데이터만 |
| 권한 | 관리자 / 사용자 구분 | 관리 기능은 사용자 화면과 분리 |

폴더로 보이게 한다: `src/server/import`, `src/server/core`, `src/server/publish`, `src/server/read` (웹이면 docs/ARCHITECTURE.md 3장)

### 운영 리스크 점검 (작게 대비하거나 리스크 표에 기록)

| 리스크 | 작게 대비하는 법 (10~15분) | 설명할 대안 |
|---|---|---|
| 동시 수정 | 설정·데이터에 `version` 컬럼, `UPDATE … WHERE version=?` 실패 시 409 | 무거운 재계산은 한 번에 하나 (잠금·작업 큐, DB 쓰기 트랜잭션) |
| 서버 장애 시 조회 | 게시할 때 결과를 정적 JSON으로 저장, 화면에 기준 시각 표시 | 클라이언트 캐시(localStorage·서비스 워커), 인쇄본·공지 병행. "쓰기는 멈춰도 읽기는 산다" |
| 잘못된 입력 | 업로드 시 필수 컬럼·형식·범위·중복 검사, 실패 행 보고 | 검증 실패 시 기존 게시본 유지 |
| 개인정보·권한 | 조회 응답에서 민감 필드 제거 (서버에서) | 본인 인증, 최소 정보만 응답 |
| 규칙 변경 파급 | 변경 후 재계산은 초안으로 | 변경 전후 비교 후 게시 |
| 실행 불가 조건 | 제약을 못 맞춘 대상을 명시적으로 보고 | 조용히 빼지 않기, 관리자에게 경고 |
| 규모 증가 | 계산 시간 측정 출력 | 계산은 게시 시점에만, 조회는 확정본 |
| 변경 이력 | 게시 시 버전·작성자·시각 기록 | 되돌리기 |

담당자가 요청하지 않은 대비를 크게 만들지 않는다. **작게 구현하거나, DECISIONS.md 8번 표에 "상황 → 파급 → 대안"으로 남긴다.**

## 6. 기록: 언제 무엇을 말하나

담당자 DM은 Codex가 볼 수 없다. **합의 내용은 내가 옮겨야 기록된다.**
AGENTS.md에 "누적하라"는 규칙이 있어도 코드에 집중하면 빠뜨린다. 정해진 순간에 한 줄씩 말한다.

### 파일별 갱신 방식

| 파일 | 갱신 방식 | 누가 언제 |
|---|---|---|

### 빠뜨림 잡기

- 답변 끝 `문서 갱신 없음` + 방금 중요한 결정을 했다 → "그 결정 기록해"
- `기록 제안: …`이 나오면 맞는지 보고 "반영해" 또는 무시
- 내 터미널 탭: `git diff DECISIONS.md` 로 방금 바뀐 행 확인

| 2 | Chrome DevTools MCP | 콘솔 에러, 네트워크, 접근성 점검 | `WITH_BROWSER_MCP=chrome` | `--no-usage-statistics --no-performance-crux` (스크립트가 설정) |

| 2 | `security-best-practices` 스킬 (OpenAI) | 마무리 보안 점검 | Codex 안에서 `$skill-installer security-best-practices` | 없음 |

**언제 추가하나**
- 시작 시: Context7, Next.js DevTools (Next.js 프로젝트를 만들고 dev 서버를 내 터미널 탭에서 띄운 뒤부터 쓸모 있음)

## 11. 서술형 (AI 없이 직접 타이핑, 문항당 5분)

**3단계로 쓴다**
1. **약점 지점**: 파일·함수·규칙을 구체적으로 지목
2. **파급**: 왜, 누구에게, 어떻게 위험한가
3. **다음 계획**: 무엇을 검증·개선할 것인가

**자주 나오는 질문 유형과 답의 재료**

| 유형 | 예 | 답의 재료 |
|---|---|---|
| 운영 장애 | "여러 관리자가 동시에 수정하면?" "보는 중에 서버가 죽으면?" | DECISIONS.md 8번 리스크 표, ARCHITECTURE.md 6·7장 |
| 권한·개인정보 | "관리자와 사용자를 어떻게 나눴나?" "남의 정보가 보이지 않나?" | ARCHITECTURE.md 4장, 권한 매트릭스, toUserDto |
| 상태 관리 | "왜 전역 상태를 썼나?" | ARCHITECTURE.md 8장 (화면 상태·캐시에만) |
| 검증 | "AI 말만 믿지 않고 어떻게 확인했나?" | VERIFY.md "실행자: 나" 항목, 발견한 문제 |
| 구조 | "업로드·계산·조회의 책임을 어떻게 나눴나?" | DECISIONS.md 5번 구조 표, ARCHITECTURE.md 13장 |
| AI 활용 | "AI의 한계를 어떻게 극복했나?" "핵심 기능을 AI와 어떻게 만들었나?" | AI 판단 기록, 내가 정한 제약과 지표 |
| 설계 근거 | "왜 이 알고리즘·방식인가?" | 결정 → 근거 → 한계와 대안 |

**검증 질문 답안 틀**
> AI가 작성한 테스트와 별개로 ○가지를 직접 확인했습니다. (작은 케이스) (불변 조건) (테스트를 테스트).
> 이 과정에서 ○○ 오류를 발견해 수정했습니다(커밋 ○○). 다만 ○○는 검증하지 못해 다음에는 ○○로 확인하겠습니다.

**전제가 틀린 질문은 바로잡는다**: "○○는 구현하지 않았습니다. 이유는 ~, 대신 ~"
**구현하지 않은 것을 물으면**: 지금 구조의 어디에, 어떻게 넣을지로 답한다.

250~400자, 구체적인 함수명과 숫자. 제출 전 DECISIONS.md 5·8·9·11번과 VERIFY.md를 다시 읽는다.

| MCP 추가 실패 / `/mcp`에 안 보임 | Codex 재시작 후 한 번만 재확인, 안 되면 그 도구 없이 진행 |
| 브라우저 MCP가 브라우저를 못 띄움 | 바로 포기, 플랫폼 Browser 미리보기로 직접 확인 |
| 플랫폼 오류 반복 | 상단 "문제 신고" (시각, 직전 동작, 오류 문구) |
